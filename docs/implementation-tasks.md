# GrainBasket v1.0 implementation tasks

Build **admin web and API foundation → store Android and order operations → consumer Android and release**. The single [v1.0 PRD](prd-v1.0.md) is the acceptance baseline; **both Nagpur stores and all three apps ship together**. Apply [001](../services/api/migrations/001_phase1.sql), [002](../services/api/migrations/002_phase2_store_offers.sql) and [003](../services/api/migrations/003_v1_otp_and_store_audit.sql) in order to a fresh database before configuring either store. The historical migration name does not defer second-store functionality. The [roadmap](implementation-roadmap.md) defines stage gates; application folders stay placeholders until their stages begin.

## 1. Admin web and shared API foundation

- [x] **A1 — Bootstrap the API and admin app.** Set up the Node.js service, PostgreSQL migration runner, React app, environment configuration and local start/test commands. Apply all versioned migrations in order and verify a health check; keep database credentials on the server and document HTTPS deployment requirements.
- [x] **A2 — Secure staff access.** Implement hashed staff/admin passwords, revocable sessions, active-account checks, server-side role and store authorization, and secure admin cookies with CSRF protection. Admin can sign in/out; staff credentials cannot access admin settings; deactivation invalidates access.
- [x] **A3 — Configure both stores.** Implement admin store selection and APIs/screens for each store's identity/contact, daily hours and closures, cutoff, pickup slots/lead time, delivery pincodes/fee and ordering switch. Keep order acceptance disabled until the selected store is configured; the public availability API rejects its closed hours and unsupported pincodes. Server-calculated quotes follow in S1.
- [x] **A4 — Publish catalog, offers and rewards.** Implement shared flour/rice categories, weight/rice-age variants, image references, English/Hindi/Marathi content and per-store offers with independent price, stock and active state. Add store-assigned staff accounts, per-store reward rules, shared customer points in the data model and English fallback. Validate claim evidence and stock; restrict these writes to admin. Customer balance transactions follow in S3.
- [ ] **A5 — Verify the admin foundation.** Configure both stores with different hours, delivery coverage, staff and flour/rice offer prices/stock in the three-language React panel; confirm unauthorized access is rejected and the API serves the selected store's catalog and schedule. Follow the [admin acceptance requirements](prd-v1.0.md#admin-web).

## 2. Store Android and order operations

Depends on A1–A4. The API remains the owner of pricing, stock, payment and status changes.

- [ ] **S1 — Implement selected-store quotes and atomic checkout.** Add server-calculated quotes for the chosen store's offers, schedule and delivery coverage, historical order snapshots, idempotent order creation, stock/point reservations with expiry and staff cash collection in the same transaction as a placed order. No mixed-store order or cross-store stock use; concurrent checkouts cannot oversell or spend points twice, and retries return the existing outcome.
- [ ] **S2 — Integrate online payment and refunds.** Select the gateway during implementation. Add provider-hosted UPI/card attempts, authenticated callback verification, duplicate/late callback reconciliation, payment expiry, stock release and tracked online/cash refunds. Neither Android client nor admin can mark online payments paid; pending attempts stay out of the fulfillment queue.
- [ ] **S3 — Enforce operations, rewards and OTP.** Add store-scoped paid queue, valid pickup/delivery transitions, flour arrival and estimate actor/history, reasoned stock adjustments, cancellation/refund initiation, completed-order point awards/restoration and one shared balance across stores. Implement OTP issuance/verification for staff points use and later consumer login: keyed digest, short expiry, attempt limits and atomic one-time consumption. Across both apps and all purposes, atomically claim `otp_request_cooldowns` for the normalized mobile only if `next_request_at` is at or before the database request time; use a conditional insert/update returning the accepted row, with challenge creation and prior unused challenge invalidation in the same transaction. Before **30 seconds**, reject without SMS or a new challenge, return the remaining wait and do not advance the row. Keep the cooldown record through expiry/consumption; initiate one SMS per accepted claim without automatically duplicating uncertain sends. Test at 29/30 seconds, after consuming/expiring a code and with simultaneous requests.
- [ ] **S4 — Build staff order entry in Compose.** Add store-assigned staff sign-in, three-language UI, assigned-store cart/quote, required customer name/mobile, pickup/delivery and flour options, separate optional marketing choice, cash confirmation and hosted online checkout. Verify the phone through the shared OTP service only for redemption or claiming unverified staff-order points; show the remaining 30-second resend wait. Ordinary staff entry does not require the consumer app.
- [ ] **S5 — Build staff fulfillment in Compose.** Show only the signed-in store's paid orders and separate pending attempts; check in arrivals, prepare/ready with delayed estimate/reason, hand over, cancel and correct stock. Reject cross-store access; after uncertain network results, refresh before allowing another action.
- [ ] **S6 — Complete admin reconciliation and review.** Add per-store views for order source, cash versus verified online attempts, cancellations, refund progress, manual cash refunds and reward corrections with reason and staff actor. Report placed/completed/cancelled orders, payment failures/refunds, stock changes and flour readiness per store. Verify cash and online cancellations reconcile without duplicate refunds or points; follow the [store](prd-v1.0.md#store-android) and [admin](prd-v1.0.md#admin-web) acceptance requirements.

## 3. Consumer Android and v1.0 release

Depends on the verified S1–S6 order and payment paths; reuse them rather than building a second checkout.

- [ ] **C1 — Add customer identity and read APIs.** Reuse S3's OTP service and 30-second mobile cooldown across both apps; add consumer sign-in, sessions, order ownership, shared reward balance/history and marketing choice/withdrawal. Show remaining resend time and reject invalid, expired, consumed or over-attempted codes. Browsing stays public; one customer cannot read another's order or points.
- [ ] **C2 — Build browse and fulfillment in Compose.** Add persisted English/Hindi/Marathi choice, explicit store selection, pincode-filtered eligible stores, selected-store translated flour/rice offers with English fallback, cart/grind choices, configured hours, delivery and both flour pickup modes. Switching stores clears/reconfirms the cart; reject inactive stock, closed windows, unsupported pincodes and unavailable times on the server.
- [ ] **C3 — Build customer checkout.** Confirm a selected-store quote and minimum-balance redemption from the shared points balance; start hosted UPI/card payment and show pending until server verification. Requote on store switch, changed prices, stock or points; retries must not duplicate charges.
- [ ] **C4 — Build history and tracking.** Show the customer's orders labeled with the selected store, flour arrival/requested/updated estimate, fulfillment status, refund progress and earned/used points across both stores on refresh. Allow cancellation of an owned `PLACED` order before acceptance; never show ready or refunded solely because the client expects it.
- [ ] **C5 — Verify the complete v1.0 release.** Exercise consumer online orders and staff cash/online orders for pickup and delivery across both stores in all three languages; check independent offers/stock/hours/coverage, both flour modes, admin reconciliation, payment failure/late success, duplicate checkout, stale quote, cancellation/refund, points restoration and cross-store/account denial. Check OTP sends none at 29 seconds, allows a new challenge at 30 seconds and sends at most one SMS under concurrency. Configure real store/reward/tax/provider values and test backup/restore before accepting live orders; follow the [v1.0 acceptance requirements](prd-v1.0.md#data-deployment-and-release-acceptance).

The future iOS consumer app is a separate later task and reuses the v1.0 API/customer records.
